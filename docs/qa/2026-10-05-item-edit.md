# QA report - item Edit page - 2026-10-05

Scope: the item Edit page (commits f0e3f11, ef98752): view mode, Edit form for task/event/note, Type chips, change by voice/text, unsaved drafts, recording section, i18n, nearby regressions |
Builds: web/mobile/backend at commit ef98752 |
Environment: QA API :58600, account feedtest (profile TZ Europe/Moscow, Chrome TZ America/New_York to catch device-vs-profile mixups), Chrome 420 + 1280, emulator yes (view + Edit screen only) |
AI calls used: 20 of 25

## Summary
The basic form works well: every field saves correctly in the profile timezone, validation and Save-disabled states are right, Cancel discards hand edits, the type chips convert with the created date and reminders kept, the mic shortcut auto-starts recording, and the recording section (delete / Undo / Cancel keeps / Save deletes) behaves. The problems are in how the form combines with the server: a type change **drops an event's location**, a Save that fails after the type change **strands the user on a deleted item**, discarding the form's addition from the feed banner makes the form **impossible to save**, and the follow-up review for "unrelated" words **captures twice** and leaves a pending review behind. Merging AI proposals also has issues: hand-removed reminders come back, a later addition can't correct an earlier one, an unusable date ("31 February") moves the event to today, and added details start with a stray ". ". Mobile was checked by reading code (it uses the same `shared/itemForm.ts`, so findings 1-10 apply there too) and by a quick look on the emulator.

### 1. Changing an event to a note/task in Edit loses its location (and people)  (Bug, confidence: high)
- Steps: 1. Event "QA event to note" with location "Room 42", people Anna, Boris, description "Agenda here". 2. Edit → Type chip Note → Save.
- Expected: CLAUDE.md: "location goes into the text where the type has no field for it". `POST /api/items/convert` alone gives `"Agenda here\n\nLocation: Room 42"`.
- Actual: the note's content is `"Agenda here"`. The same happens for event → task (description "Agenda here"). Location and people typed into the form before switching are lost too.
- Evidence: `tools/qa/out/ie3.cjs` output (API convert vs UI convert, side by side).
- Where: `shared/itemForm.ts` `saveItemForm`: convert puts the location into the text, then the follow-up `notes.update` / `tasks.update` overwrites it with `form.details`.
- Suggestion: when the form's type has no location/people field, fold them into `details` before the PUT (or don't PUT the text after a convert).

### 2. If Save fails after the type change, the old item is gone and the form can never be saved  (Bug, confidence: high)
- Steps: 1. Task with a date/time → Edit. 2. Title of 301 characters, Type chip Event. 3. Save. 4. Fix the title, Save again.
- Expected: either all of it is saved or none of it is.
- Actual: step 3: `POST /items/convert` succeeds (the task is soft-deleted, a new event exists with the old title), then `PUT /appointments/{new}` returns 400. The editor stays open on the deleted task's URL with the error. Step 4: `POST /items/convert` → 404 "Item not found." on every retry. The user's edits are stuck in a form for an item that no longer exists, and the draft is stored under the old id.
- Evidence: `tools/qa/out/ie3-partial.png`, `ie3-partial-retry.png`; old task GET → 404; feed shows "Appointment: QA partial fail 2".
- Where: `shared/itemForm.ts` `saveItemForm` (convert, then update, as separate requests); `ItemEditor` keeps `item.id`.
- Suggestion: after a successful convert, carry on with the new id (or navigate to it) even if the PUT fails; better, validate before converting.

### 3. The form's unsaved addition appears in the feed banner; discarding it there makes Save fail forever  (Bug, confidence: high)
- Steps: 1. Task → Edit → hand-edit Notes, type "Make it high priority." 2. Press Back (in-app). 3. The feed's capture bar shows "Unsaved addition to “QA draft task” · Resume · Discard". 4. Discard. 5. Open the task → Edit (draft restored) → Save.
- Expected: one place to finish the change; Save in the form works.
- Actual: Save shows "Some items were already saved or rejected. Reload the capture." every time. The PUT already went through (priority High and the notes are saved on the server), only the `linkOnly` confirm fails, so the form never closes; only Cancel gets out. "Resume" in the banner would open the old review for the same addition, so the same change can also be applied from two places.
- Evidence: `tools/qa/out/ie6-feed-banner.png`, `ie6-save-after-discard.png`; 3× `POST /captures/{id}/confirm` → 400.
- Where: `web/src/lib/usePendingReview.ts` / `shared/pendingReview.ts` don't know about edit-form proposals; `saveItemForm` treats the confirm failure as a Save failure.
- Suggestion: leave proposals that belong to a stored edit draft out of the banner, and ignore already-decided proposals in `linkOnly`.

### 4. The follow-up review captures the words twice; the second capture is left pending  (Bug, confidence: high, 2 of 2)
- Steps: 1. Task → Edit → "Ask him about the kitchen light as well. Also call mom tonight." → the "Also capture … as a new entry" offer appears (checked). 2. Save → the review for "Call mom" appears. 3. Save all.
- Expected: one capture, saved; the review closes.
- Actual: right after Save all, a second capture of the same words is made ("Call mom tonight", one more OpenAI call) and its review shows again (first run) or is left pending (second run, note "Book a table" / "Book Friday table"). Both leftovers then show in the feed banner "Unsaved review … Discard all 2".
- Evidence: `ie5` / `ie8` output (captures list: "Call mom" pending 0 + "Call mom tonight" pending 1; "Book a table" pending 0 + "Book Friday table" pending 1); `tools/qa/out/ie11-feed.png` banner.
- Where: `web/src/components/ItemEditMode.tsx` `FollowUpReview`: the capture is a `useQuery(['follow-up', text])`; saving the review invalidates all queries, so the active query refetches = `POST /captures/text` again. Same code in mobile `ItemEditMode.tsx`.
- Suggestion: make it a one-shot mutation (or exclude the key from invalidation / `enabled: false` after the first result).

### 5. Any addition brings back a reminder removed by hand and marks Reminder as changed  (Bug, confidence: high)
- Steps: 1. Event with reminders "1 hour before" and "Every day at 8:00". 2. Edit → remove "1 hour before" with ×. 3. Type "Olga is bringing her husband."
- Expected: reminders untouched (the AI didn't change them); no Reminder mark.
- Actual: "1 hour before" is back, and Reminder is marked as changed by the AI. The same spurious mark appears on every addition to an item that has reminders (e.g. the "31 February" case).
- Evidence: `ie9` output: saved reminders carry `nextAtUtc: "2026-10-09T08:00:00Z"`, the proposal's carry `nextAtUtc: null`; `tools/qa/out/ie9-info-only.png`.
- Where: `shared/itemForm.ts` `sameReminder` compares `JSON.stringify` of the whole reminder, including `nextAtUtc`, so every saved reminder looks "removed" and every proposed one "fresh".
- Suggestion: compare kind/atUtc/minutesBefore/time/days only (as `ContinuedItem.SameReminder` does on the server).

### 6. A second addition can't correct the first  (Bug, confidence: medium)
- Steps: in one Edit session: "Make it high priority and remind me 30 minutes before." then "Actually remind me 1 hour before instead of 30 minutes." → Save.
- Expected: one reminder, 1 hour before.
- Actual: both "30 min before" and "1 hour before" are shown and saved.
- Evidence: `ie4` output (A3, saved reminders `Before60, Before30`).
- Where: the continue call sends the item as saved, so the AI never sees the form's unsaved additions; `applyProposal` only adds what differs from the saved item.
- Suggestion: send the current form state as the item the AI works on (or treat the latest proposal for a field as replacing the earlier one).

### 7. An unusable date moves the event to today and marks Date as changed  (Bug, confidence: high, 2 of 2)
- Steps: event on Oct 8/9 → Edit → "Move it to the 31st of February."
- Expected: the clarification ("February has no 31st — what date did you mean?") and the date left as it was.
- Actual: the clarification is shown, but Date becomes today (2026-10-05) and is marked; Save would move the event to today.
- Evidence: `ie8`/`ie9` output: the proposal returned `startUtc: 2026-10-05T09:00Z` with the clarification; `tools/qa/out/ie8-clar.png`.
- Where: server normalizer/`ContinuedItem.Keep` falls back to today for a continued item; `applyProposal` applies it anyway.
- Suggestion: for a continued item, keep the saved date/time when the new one is unusable (or don't apply fields from a proposal that has a clarification).

### 8. Cancel keeps the cancelled words in the transcript and the cancelled audio in the recording  (Bug, confidence: high)
- Steps: 1. Item from a typed capture → Edit → "Move it to Monday." → Cancel. 2. Voice item → mic shortcut → speak → Send → Cancel.
- Expected: CLAUDE.md / the page: "Nothing is saved until Save; Cancel drops it all".
- Actual: the item and its proposal are fine (proposal Rejected, item unchanged), but the view's source card shows "Move it to Monday." under "What you typed"; for voice, the recording went from 1 to 2 parts and the transcript contains the cancelled words. For an item made by hand, the first addition also creates and links a capture immediately, so a cancelled addition leaves a "From a typed capture" card with words that were never applied.
- Evidence: `ie5` output (`input: "...\n\nMove it to Monday."`, source card has Monday), `ie7` output (`after cancel: parts 2`).
- Where: `POST /captures/{id}/continue` appends text/audio before the user decides; `discardProposals` only rejects the items.

### 9. Added details start with a stray ". "  (Bug, confidence: high, 2 of 2)
- Steps: task with details "Leak under the sink" → "… The door code is 1234."
- Expected: "Leak under the sink. The door code is 1234." (or the new sentence on its own line).
- Actual: "Leak under the sink\n\n. The door code is 1234." Same with the voice item: "for the fence\n\n. Get the white one." This gets saved.
- Evidence: `ie4` output (A1, saved description), `ie7` output.
- Where: `shared/itemForm.ts` `applyProposal`: `text.slice(saved.details.length)` keeps the AI's joining punctuation, then `join` adds "\n\n".
- Suggestion: strip leading punctuation/whitespace from `added`.

### 10. Saving an open form silently overwrites a newer change made elsewhere  (Bug, confidence: high)
- Steps: 1. Task → Edit → change Notes. 2. Elsewhere (API = another device) rename it and set priority Low, tags/reminders cleared. 3. Save the form.
- Expected: the newer change is kept, or at least a warning (CLAUDE.md: optimistic concurrency → 409); the brief: "draft must not overwrite it".
- Actual: Save puts back the form's stale title "Renamed elsewhere" and priority Medium; the other change is gone without any message. (The *stored* draft case works: when the item changed, the draft is not restored.)
- Evidence: `ie6` output ("after save over a newer change: title Renamed elsewhere prio Medium").
- Where: `saveItemForm` PUTs every field; the update requests carry no row version.
- Suggestion: send only changed fields, or compare `draft.saved` with the freshly fetched item before saving.

### 11. "Also buy milk on the way home" went into the details instead of being offered as a new entry  (UX, confidence: medium, AI-dependent)
- Steps: plumber task → "Bring the blue toolbox. Also buy milk on the way home."
- Actual: both sentences in the details, no "Also capture…" offer. "Also call mom tonight" and "Also book a table for Friday" were offered correctly.
- Evidence: `ie4` output (A4).

### 12. Ongoing task with a "before" reminder: "Add a time…" while the time field is disabled  (UX, opinion)

## What works well
- View mode (web + emulator): Complete / Cancel task / Edit / mic / Delete only; no Type chips, "Add more" or "Delete recording"; source card read-only; floating dock hidden on the item screen on mobile.
- Task form: title, date, time, priority, tags (trimmed, de-duplicated, existing tag reused), description, notes, Ongoing, reminders Before / At / Weekly — all saved correctly in the profile timezone (Moscow) while the browser was in New York (23:30 → 20:30Z).
- Validation: empty title, time without date, event without time, note reminder rules — Save disabled with a clear message; Cancel discards hand edits.
- Type chips: task → event keeps date/time/reminders/notes, end = +1 h; event → note turns "15 min before" into an At reminder at the right moment; note → task; created date kept every time; navigates to the new item; no 404s in the browser.
- Voice/text: changed fields are marked; a hand edit made between two additions survives (priority Low kept, tags/notes kept); type change by text ("Make it an event tomorrow at 5 pm") converts and opens the new event with the capture linked; info-only additions go to details; clarification text is shown; unrelated words offered as a checkbox.
- Mic shortcut starts recording at once; voice addition via fake mic works; recording section: play this part, speed chips, mark for deletion, Undo, Cancel keeps, Save deletes.
- Hand-made items get a capture on first use (one `for-item` call); none is shown before anything is said.
- Draft restore after leaving and coming back; not restored when the item changed meanwhile; reload warns.
- Russian and Hebrew: all new texts translated; Hebrew layout mirrors correctly at 420; no horizontal overflow.
- Regressions nearby: feed loads, new typed capture → review → Save all works.
